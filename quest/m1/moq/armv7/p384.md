# [L] P-384 on armv7

## Goal

On armv7, rind signs and verifies ECDSA P-384, generates P-384 keys, and
agrees P-384 ECDH keys through the same API as the other arches, so moq-auth's
ES384 tokens, P-384 TLS keys, and P-384 key exchange in TLS and DTLS work on
the armv7 release.

## Plan

Settled (maintainer, 2026-10-27): libcrux has no P-384 ECDSA, so rind builds
signing, verification, and key generation over libcrux-p384's field and
scalar arithmetic, with RFC 6979 nonces and constant-time inversion, rather
than excluding P-384 from armv7. ECDH comes along because armv7 covers every
operation the other arches do, and `rind-rustls` and `rind-dimpl` offer P-384
key exchange.

Open question for the maintainer: libcrux-p384 0.0.1 exports only ECDH
(`derive_ecdh` and its key types); its field and scalar arithmetic is
`pub(crate)`, so the settled plan cannot build ECDSA on it as published.
Options: get libcrux to export that arithmetic, or take the field arithmetic
from another verified source such as fiat-crypto's P-384. ECDH alone can use
`derive_ecdh` today.

Until this lands, armv7 compiles out `key_agreement::p384` and
`signing::ecdsa::P384`, and `rind-rustls` gates its P-384 key exchange,
signer, verifiers, and tests with `cfg(not(target_arch = "arm"))`; remove
those gates here.

Guidance:

- Scalar multiplication, inversion, and point validation must be constant
  time in the secret scalar; add ctgrind coverage.
- Reject invalid points and out-of-range scalars and signatures with errors.
- Test with Wycheproof's P-384 ECDSA and ECDH vectors under qemu, and
  differentially against aws-lc-rs.
